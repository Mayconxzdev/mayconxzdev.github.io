Before

Documents, certificates and non-conformities were distributed across shared folders and part of the review meant checking files one by one. The risk was not only time: expired information or a hard-to-find pending item made audits and follow-up harder.

The pilot

The scanner reads the source, hashes what it finds, reprocesses only changed files, extracts content locally and sends structured data to a Rules Engine. The interface surfaces pending items and evidence, while the final conclusion remains with the Quality owner.

Why I did not put an LLM in charge of compliance

I wanted every alert to be explainable. Critical rules remain deterministic. AI can help with retrieval or summarization later, but it should not become a black box deciding whether something is compliant.

Security from the design stage

  • document source mounted read-only;
  • synthetic data in the public edition;
  • no real credentials in Git;
  • local processing by default;
  • human review for sensitive decisions.

Architecture at a glance

Document repository → Python scanner → local extraction → SHA-256/classification → SQLite/PostgreSQL → Rules Engine → FastAPI → dashboard/Tauri

n8n schedules scans, queries and alert/recovery flows through the API. Docker Compose keeps the demo reproducible.

If you want to review the code

I would start with app/, n8n/, tests/, docker-compose.yml and docs/CASE_STUDY.md. The repository was sanitized to avoid publishing private IPs, network paths or corporate data.

What I would do differently today

I would separate document inventory, domain rules and interface earlier. The pilot made it clear that the real value is not simply “reading PDFs”; it is being able to show which rule created a pending item and which evidence led to the alert.

Real scope

Central ISO is a functional technical pilot. I do not claim ISO certification, automatic compliance, corporate SSO, running RAG or official production deployment. I prefer to show exactly how far the project went.
